# HackthonSpurs engineering rules

- Read the [DeValpo engineering skill](.agents/skills/devalpo-engineering/SKILL.md), [maintained architecture](docs/ARCHITECTURE.md) and affected contracts before editing.
- Keep each class at **200 physical lines or fewer**, including blank lines and comments between the declaration and closing brace. Count C# partial declarations together, including committed generated parts. Split by responsibility, not into arbitrary partials.
- Run `pwsh -NoProfile -File tests/quality/Test-ClassSize.ps1` at the Git root. For TypeScript and React, `npm --prefix frontend run lint` uses a stricter 200-line limit per source file, also covering function components. Python test modules use the same conservative file limit.
- For backend project or dependency changes, run `python -B tests/quality/test_backend_layout.py`; keep the [project ownership map](docs/ARCHITECTURE.md#4-projects-and-dependencies) in sync. Keep backend projects physically under their matching solution group; do not add a flat project at the backend root.
- Write project documentation in English. Use only synthetic fixtures in version control and tests; never publish local demo data, uploads or secrets.
- Document each hand-written named function, method and constructor in English at its declaration. Describe its behavior and the meaning of its inputs (excluding implicit receivers). Keep inline callbacks local; do not rewrite generated code or historical migrations for style.
- Place each backend interface alone in `<feature>/Contracts/I<Role>.cs`. In Application, match each file name to its one top-level type; keep records and enums in the feature’s `Models/` folder. Preserve existing feature namespaces. Keep read ports in Queries/Contracts and mutation ports in Commands/Contracts; processing and embedding ports stay with those use cases. Add PostgreSQL implementations to HackthonSpurs.Persistence, not duplicate interfaces beside the adapters.
- Keep document commands and read-only projections separate. Put technical retries in Application, PostgreSQL claim/publication SQL in Persistence, and polling and fixture selection in Worker. Domain rules must not depend on Application; neither layer may import a host or provider. Run `dotnet run --project tests/application -c Release` for the use-case checks; see the CQRS section of the maintained architecture. Follow the root EditorConfig for indentation.
- Keep backend errors, messages, setting names, operational defaults and application literals in the [shared catalog](docs/backend-resources.md). Regenerate bindings and run `tests/quality/Test-BackendResources.ps1`; do not store credentials there.
